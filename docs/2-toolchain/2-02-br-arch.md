## 0. 一句话定位

`br` = **组合期(host 侧)工具**: 把「插件树 + 产品 manifest + 平台参数」解成「依赖闭包 + 初始化顺序 + 资源配置」, 生成构建输入, 再驱动编译/链接/运行/验证, 把 `1-02` 的三层契约门禁变成一条命令。

三条不可动摇的约束(已有决策, 不是本篇的选项):

1. **纯静态组合**(主文档 §12): v1/v2 无加载器 ⇒ `br` 是唯一的"组合时刻"; 运行期零检测(主文档 §6.5)。
2. **真值在构建产物**(`1-02` §2.6.1/§2.6.4): 头文件是声明真值, 符号表/布局是机器真值, 文档与生成物都是衍生物。
3. **生成物不手改**(与 golden 同纪律): `br` 的输出是衍生物 —— 改输出 = 改输入后重跑。

## 1. 职责 / 非职责

| | 内容 |
|---|---|
| **职责** | 插件发现与布局校验(`4-02`); manifest/描述符解析与一致性校验(`4-03`); 依赖闭包 + 版本区间交集求解(`4-04`); init-DAG 拓扑与**环检测**(主文档 §6.4-2/§6.5); 分类学约束与资源预算(§6.4-3/§6.4-5); 生成物(manifest.c/h、链接脚本片段、挂载计划表、init 顺序表、trace id 表); 构建编排; host/QEMU 运行; conformance 矩阵运行(`6-01` §2); golden 生成与比对(`1-02` §2.6.4); 调试解码(`5-01` §1) |
| **非职责** | 目标端运行期加载/编排(`3-05`); 契约语义的定义(`1-02`/`4-03`/`4-04`); 编译器/链接器/调试器本体(只编排, 不替代); CI 调度与产物归档 —— `br` 只保证**机器可读输出 + 稳定退出码** |

## 2. 设计必须满足的事实约束

| # | 约束 | 出处 |
|---|---|---|
| C1 | 闭包求解发生在编译**之前**, 但描述符是 C 结构体(编译期产物) | `4-02` §1; `4-03` §1(双真值问题) |
| C2 | M0 验收就是"故意造环看组合器报错" ⇒ `br` 最小形态必须在 M0 存在, 而 roadmap 把"CLI"排到 M3 | `1-03` §3 M0 / M3 |
| C3 | host 平台插件把同一套语义用例跑成 Linux 进程 ⇒ 需要**双后端**(host-native / QEMU target), 且是同一命令 | `1-03` §5 第 6 项; `6-01` §2 |
| C4 | golden 必须**独立重生成**比对, 防手编 | `1-02` §2.6.4 |
| C5 | `abi_id` = 工具链 + ABI 影响选项指纹, 二进制分发(远期 .a)要匹配 | 主文档 §6.1 / §6.4-6 |
| C6 | manifest 表达格式(YAML/TOML/DSL)、构建系统(make/cmake/自研)、插件树组织三项**均未定** | `4-03` §3; `2-01` §3; `4-02` §3 |

C1 + C2 直接决定两件先决事: **声明面必须独立于编译**(否则要么两阶段构建, 要么工具永远在编译之后才能报错), 以及 **`br` 的 M0 形态是"求解器 + 可解释报错", 不是"全功能 CLI"**。

## 3. 关键架构决策(待拍板)

### BR-D1 — 工具形态

| 备选 | 说明 | 权衡 |
|---|---|---|
| A 单体 CLI | 一个可执行文件, 子命令全内置 | 最简单; 但 CI/IDE/脚本只能走命令行文本, 逻辑无法复用 |
| **B 核心库 + 薄 CLI** | 领域模型/求解/生成做成库, CLI 只是前端之一 | 多一层接口纪律; 换来 IDE/CI/其他语言可嵌入 |
| C 可扩展子命令 | `br-<cmd>` 外部发现(类 git/cargo) | 与"一切皆插件"哲学一致; host 侧引入版本/信任负担, v1 不划算 |

**倾向 B**; C 留作 v2+ 生态位。**理由**: 求解器与生成器要被 CI 直接调用(`1-02` §2.6.4 的"独立重生成"不该靠 shell 拼装), 库化让 `br check` 与 CI 脚本共享同一实现。

### BR-D2 — 声明面与"双真值"(C1 的解法)

| 备选 | 说明 | 权衡 |
|---|---|---|
| A 先元数据编译 | 只编译描述符 TU, 拿到 deps 再全量构建 | 两阶段构建; "编不过就求不了解", 报错时机太晚 |
| B 源码静态解析 | 抓 `BR_PLUGIN(...)` 宏(正则/预处理) | 脆弱: 宏展开/条件编译都能骗过它 |
| **C 声明面唯一真值** | 每插件一份**声明片段**(人写, 插件级真值) → `br` 读它求解 → **由片段生成描述符 C 代码**(`BR_PLUGIN` 展开) | 单一事实源, 求解不依赖编译; 代价是描述符宏形态必须先定稿 |

**倾向 C**。它顺带解掉 `4-03` §1 的"双真值"问题: 描述符不再是第二真值, 而是**生成物**; `br check` 的一致性校验从"两处比对"降级为"生成物是否最新"。产品 manifest 只做"选谁/预算多少/产品参数", 不重复声明插件自身的 deps/res。**代价**: `4-02` §1 记录的描述符宏形态矛盾(`static` 近零导出面 vs 非 static)必须与生成器一起定稿。

### BR-D3 — 实现语言与运行时

| 备选 | 优点 | 代价 |
|---|---|---|
| **Python 3(锁版本单 venv)** | 文本/schema/图算法生态最好; 迭代快; CI 亲和 | 需运行时; 依赖漂移需锁; 启动慢 |
| Go 单二进制 | 无运行时依赖、跨平台、启动快、CI 可复现性强 | YAML/schema/模板生态一般; 团队熟悉度待定 |
| Rust | 同上 + 类型强 | 开发速度最慢, 与设计期高频改动不匹配 |
| 混合(核心 Go + 脚本 Python) | 各取所长 | 两套语言/两套 CI, v1 不划算 |

**倾向: Python 3 先行**(v1), 并把"**无第三方依赖**"当纪律(标准库 + 一个 YAML 解析器); 若 CI 可复现性成为痛点, 再评估用 Go 重写核心库 —— BR-D1 的库边界就是为这次替换留的门。

### BR-D4 — 构建后端边界

| 备选 | 说明 |
|---|---|
| **A 生成物 + make** | `br` 只生成 + 编排 + 增量判断, 编译交给 make(`2-01` §3 的倾向) |
| B 直出 ninja | 跳过 make, `br` 生成 ninja 文件 |
| C 自研构建 | 完全不用现成后端 |

**倾向 A**(v1): make 是嵌入式生态的通用语, 插件作者能读能改; **B 留作性能选项**(生成物形态不变, 只换后端); **C 否决**(投入产出比不成立)。

### BR-D5 — 状态、增量与可复现

- 状态目录 `build/`(不进版本库), 内含: 求解结果(闭包/拓扑/预算)、生成物、**输入内容 hash**(不按 mtime 判断, 与 `docs/render-plantuml.sh` 同一纪律)。
- 增量判断 = 「声明面 + 产品 manifest + 生成物」内容 hash 比对; 变了才重生成, 再交后端增量编译。
- **可复现性**: 镜像与产物带 `br` 版本 + `abi_id` 指纹(C5); `br env` 打印全部影响 ABI 的输入(编译器版本/选项/目标三元组)。

**倾向: 采纳**(无备选争议); 待拍板的只是"状态文件放 `build/` 还是仓库根 `.br/`"(Q5)。

### BR-D6 — target 抽象(C3 的解法)

| 备选 | 说明 |
|---|---|
| **A platform 插件即 target** | `br build --platform platform/qemu-aarch64`; host 也只是一个 platform 插件 |
| B 另立 board 描述文件 | 类似 devicetree 的独立板级文件 |
| **C A + 板级参数文件** | platform 插件是身份, 板级参数(region 表/时钟/引脚)是它的参数 |

**倾向 A + C 的最小版**: platform 插件是 target 的**身份**, 板级参数是它的参数(region 表已在插件内, 主文档 §6.3)。**host 平台插件**因此不是特例, 而是"后端为 host-native 的 platform" —— `br test` 的双后端(C3)退化成"换一个 platform 参数"。

### BR-D7 — 输出与退出码契约

- 人类可读默认输出 + `--json` 机器可读(CI/IDE/schema 校验器)。
- 退出码分层: `0` 成功 / `1` 校验红(契约违规: 环·冲突·预算超·布局违规) / `2` 用法或环境错 / `3` 编译或运行失败。
- **红必须可解释**: 环报完整路径(`1-03` §3 M0 验收), 冲突报"谁和谁在哪条边上", golden diff 报"删/签名变/布局变"三类(`1-02` §2.6.4)。

**倾向: 采纳**; `--json` schema 与 `4-03` 的 manifest schema 一次定稿(Q7)。

### BR-D8 — br 与门禁/CI 的分工

| 备选 | 说明 |
|---|---|
| A `br check` 跑三层 | CI 只调用一条命令 |
| B 只给原子命令 | `api-dump`/`test`/`verify` 各自独立, CI 自己编排 |
| **C 原子命令为真 + `check` 是默认组合** | 两个层次都给 |

**倾向 C**: 三层门禁的触发器不同(`1-02` §2.3), 原子命令让 CI 能按层并行/分阶段; `br check` 给本地开发一条命令。

## 4. 推荐架构(若 §3 按"倾向"拍板)

分层(自上而下, 每层只依赖下层; 层间用稳定数据结构通信 —— 这是 BR-D1 库化的落地):

| 层 | 职责 | 关键接口 / 产物 |
|---|---|---|
| **L5 前端** | CLI 解析、输出格式、退出码、日志 | `br <cmd> [--json]` |
| **L4 门禁** | 三层门禁的编排与比对 | `api-dump`(生成/独立比对)、`test`(矩阵)、`verify`(版本矩阵) |
| **L3 编排后端** | 构建/运行/调试后端 | build(make/ninja)、run(host-native / qemu)、dbg(解码) |
| **L2 生成器** | 输入 → 构建输入 | manifest.c/h、链接脚本片段、挂载计划表、init 顺序表、trace id 表 |
| **L1 求解器** | 闭包/版本区间/拓扑/环/预算/分类学 | 纯函数: `(插件模型, 产品模型) → 求解结果 或 诊断` |
| **L0 领域模型** | 插件/产品/平台/资源的规范化模型 | 声明片段 → 模型; 可解释的诊断模型 |
| 横切 | 内容 hash 缓存、版本戳与 `abi_id`、错误与诊断、schema 校验 | — |

三条建议直接采纳(非备选):

1. **L1 必须是纯函数且可单测** —— 环检测/闭包/预算的属性用例(含"故意造环")就是 M0 验收, 不依赖编译器与 QEMU。
2. **L0 模型与 `4-03` schema 同源** —— schema 定稿即 L0 定稿, 别让 `br` 内部模型成为第三种真值。
3. **生成物统一写进 `build/gen/` 并在文件头写"生成物勿改"** —— 与 golden 同纪律。

## 5. 命令面(草案)

| 命令 | 输入 | 产物 / 效果 | 层 | 里程碑 |
|---|---|---|---|---|
| `br init <app>` | 模板 | 产品骨架(manifest + APP 目录) | L5 | M3 |
| `br add <plugin>...` | 插件路径(`4-02` 约定) | 更新产品 manifest(闭包求解后写入) | L1+L2 | M1 |
| `br check` | 产品 manifest + 插件树 | 六项组合期校验的完整诊断(环/版本/分类学/预算/接口/abi) | L1+L4 | **M0(环检测先行)** |
| `br build` | 同上 + 平台参数 | `build/gen/*` + 镜像(或 host 可执行文件) | L2+L3 | M1 |
| `br run` | 镜像 / host 目标 | host-native 执行 或 QEMU 启动 | L3 | M2(QEMU) / M3(host) |
| `br test` | 用例集 + platform | conformance 矩阵报告(`6-01` §2) | L3+L4 | M3 |
| `br api-dump` | 构建产物 | `api/frozen/*.txt` + diff | L3+L4 | M3(`1-02` §2.6.4) |
| `br dbg` | bridge 流 / fault dump | 解码、回溯、时序对照 | L3 | M3(`5-01` §1) |
| `br new <kind>` | 类别 | 插件模板(声明片段 + 描述符骨架 + conformance 骨架) | L5 | v1.x(`4-02` §2 第 6 项; 复用 BR-D2 生成器) |
| `br show` / `br env` | — | 求解结果(闭包+拓扑+预算) / 影响 ABI 的输入清单 | L1 | M1 |
| `br pack` | 插件 / 产品 | 二进制分发件(.a + 头 + `abi_id`) | L2 | **v2+(D14 远期)** |

## 6. 与既有机制的接口

| 对手方 | 接口 |
|---|---|
| `1-02` §2.6.4 golden 管线 | `br api-dump` 生成; **CI 侧独立重生成**再比对(C4); `br` 不裁决"是不是红", 只给机器可读 diff |
| `6-01` §2 conformance | 用例表驱动契约 `{id, 前置, 步骤, 期望, 适用调度, 平台}`; host/target 双后端由 BR-D6 统一 |
| `5-01` §1 调试解码 | bridge 帧协议 / fault dump 解析器与 `br` 共享库(BR-D1 的库边界给复用留位) |
| `3-05` 运行期 | **单向**: `br` 生成 init 顺序表 + 描述符段内容 → `3-05` 只读执行; 运行期零检测(主文档 §6.5) |
| `4-02` 布局 | 插件发现 = 布局约定, `br` 是约定的执行者(强制程度 `4-02` §3 待定, 与 BR-D2 一起定) |
| `4-03` / `4-04` | 语义在彼、实现在此; schema 定稿与 L0 模型同源 |

## 7. 演进路线(与 M0–M5 对齐)

| 里程碑 | `br` 能力 | 验收 |
|---|---|---|
| **M0** | L0+L1 + `br check`(环/闭包/分类学), 声明面最小可用版 | 故意造环 → 报完整环路径(C2) |
| M1 | L2 生成器 + `br build`/`add`/`show`(make 后端) | 组合出可启动 hello 镜像 |
| M2 | QEMU 后端 + 挂载计划/描述符生成物 + 资源预算校验 | M2 四框架件 + tmpfs/devfs 组合跑通 |
| M3 | host-native 后端 + `br test`/`api-dump`/`dbg`/`init` + `--json` | 三层门禁可在 CI 一键执行; native API 冻结启动 |
| M4+ | `br new` 脚手架、多产品共库、`br pack`(二进制分发) | 真实 SoC platform 插件接入(`1-03` §3 M4) |

> **与 roadmap 的差异点(需在 `1-03` 侧对齐)**: `1-03` §3 把"CLI"排在 M3, 但 M0 的验收依赖组合器(C2)。建议明确为「M0: 求解器 CLI(最小)」+「M3: 完整体验 CLI」, 或把 M0 验收改写为"求解器库单测 + 一条命令"。
