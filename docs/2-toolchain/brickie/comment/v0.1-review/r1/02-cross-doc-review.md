## 总评(评审原文)

这份 v0.1 草案与既有文档体系的关系是**"继承为主、局部改写"**: 命令面/状态目录/退出码/环政策等大量内容确实忠实继承;但它同时**改写了 4 处既有决策**(APP 直调 native、运行时依赖声明面、描述符元契约、工具实现语言)与 **1 处分类学口径**,而 §13.2 的 A-1…A-11 清单既**漏**了 3-05 §1 / 4-02 §2-3 / 4-04 §1+§2-4 / 1-03 §1 / 1-02 §1 / 2-01 §2-4 / 2-02 BR-D3 等回灌点,又**低估**了"三态原样继承"的简化代价。

## 评审提出的"不确定/需人拍"(作者保留原样)

- **lwip/sqlite 的 `api_type` 归类未定**, 直接决定 `svc-posix`(runtime_adapter)能否依赖它们: `1-01` §6.3/§7.2 允许"服务依赖服务", `1-03` §1 说 lwip 是"svc-posix socket 路由的实现方";而草案 §3.1 规定 runtime_adapter"**只允许**依赖 native"。**若 lwip 判 `third_party`, 该必需依赖立刻变红** → 与 `r1/03` P0-3 同一问题, 双向确认。
- **框架件的"纪律同 core(golden/门禁)"在四类模型下由谁承载**: 草案 §3.3 明说 `subkind` 不承载该类属性, A-1 回灌时会把它删掉。
- **`third_party` 不抛接口 vs 运行期能力注册**: 与 BRV-Q13 同源, 既有文档无判据可核。
- **core 版本号形态**: 草案用三段 `>=1.0.0`, 而 §7.4 只定义四段操作数 → 与 `r1/03` P1-13 交叉确认。
- **三态冻结与 `6-01` 矩阵的时序**: v0.1 提供 `freeze` 但 test 排 v0.4 → 与 P0-2 同源, 需拍板。
