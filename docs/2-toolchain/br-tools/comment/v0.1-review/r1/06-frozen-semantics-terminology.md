# br-tool v0.1 设计备忘 · `frozen` 的语义与术语(解冻机制)

> **文件性质**: **设计备忘(memo)** —— 回答需求方之问: "加接口不需要解冻后更新, 而改/删已有接口必须解冻后更新, 这种行为面是否需要修改 `frozen` 语义或者换个术语描述?"
> **结论前置**:
> 1. **语义不需要改** —— `1-02` §2.1 对 `frozen` 的定义**本来就说"新增=轻量"**, 与需求方规则**零分歧**; 无需重开既有决策。
> 2. **`status = "frozen"` 的术语可保留** —— 但要补一句 gloss: 它是"**单向冻结(append-only 保护)**", 不是"面不再生长"。
> 3. **`frozen_version` 这个段名建议改** —— 它会被读成"冻结时的版本", 从而诱导**跨代比较**这一错误心智模型(而 `F` 恰恰不可跨代比较)。
> 4. **状态机缺一条路径** —— `解冻` 是**瞬态**, 必须新增; 且 release 不得停在瞬态。
> 5. **⚠ 一个关键陷阱**: "新增无需解冻"**只在条目级成立**。给一个已冻结的**结构体加字段**是"**修改**该条目" ⇒ **必须解冻**。否则 `1-01` D22 明令的"**后补字段 = 布局破坏**"会从这条缝里溜过去(D14 二进制兼容的直接漏洞)。
> **关联**: [`r1/05`](05-version-model-frozen.md)(版本模型 F1–F3 已定)。
> **状态**: §6 列 T1–T3 待拍板。

## 1. 语义: 无需修改(既有文档已经如此定义)

需求方的规则与 `1-02` §2.1 的三态表**逐字一致**:

| 出处 | 原文 |
|---|---|
| `1-02` §2.1(行 46) | `frozen` \| 进入 golden 面 \| CI 门禁硬保护 \| **新增=轻量; 语义/签名变更=决策记录+弃用周期** |
| `1-02` §2.2(行 75) | "**frozen 新增纯函数** \| 轻量: PR 说明 + 同 PR 更新 golden" |
| `1-02` §2.2(行 76) | "frozen **语义变更**(阻塞行为/错误码/ISR 安全性) \| 完整决策记录 + 弃用周期" |
| `1-02` §2.2(行 77) | "frozen **删除/签名变更** \| 决策记录 + 弃用周期" |

⇒ **`frozen` 从来就不意味着"面不再生长"**。它意味着"**已承诺的条目受保护; 新增不受限**"。需求方规则只是给这条既有语义补上了版本号格式(`F`)。

**因此**: 不需要修改 `frozen` 语义, 不需要重开 `1-02` §2.1/§2.2。这一点很重要 —— 它说明本轮版本模型修订与既有契约治理是**同一条路**上的细化, 不是分歧。

> **顺带确认(设计的主流性)**: 这个模型与 `glibc` 的 soname 演化**完全同构** —— `libc.so.6` 数十年保持 `.6` 不变, 期间新增了数千个符号; soname **只在发生不兼容变更时**才 bump。这给需求方的规则提供了工业界判例: 它是**标准的 ABI 演化模型**, 不是特例。

## 2. 术语问题一: `status = "frozen"` —— 保留, 补 gloss

**保留该词**, 但建议在 `1-02` §2.1 的表头/脚注补一句:

> `frozen` = **单向冻结(append-only 保护)**: 面**只能追加**, 不能改写/删除已承诺条目。
> 追加 ≠ 破坏承诺, 故无需解冻; 改写/删除 = 破坏承诺, 必须走解冻 → 重新冻结。

**理由**: `frozen` 是**状态名**(entries 受不受保护), 这个词在多处被引用(`BR_API_FROZEN` 宏、三态表、门禁行), 改名会波及既有文档与代码。加一句 gloss 的成本远低于改名, 且能消除"冻结了怎么还能加"的困惑。

## 3. 术语问题二: `frozen_version` —— 建议改名

### 3.1 为什么必须改

`F` 的实际语义是"**已承诺面被破坏的次数**"(一个**代数**), 但 `frozen_version` 这个名字会被读成:

| 误读 | 后果 |
|---|---|
| "冻结发生在版本 X" | 暗示 `F` 是某个**版本序列上的指针** ⇒ 会诱导"`F` 大 = 更新"的判断 |
| "`F` 参与版本比较" | 而 [`r1/05`](05-version-model-frozen.md) §5.4 明确: **跨 `F` 比较无意义**(`F=4` 可能删掉了 `F=3` 的接口, 是"不兼容的另一代"而非"升级") |

⇒ 该名字**主动邀请**它唯一不能做的事(跨代比较)。这是**命名与语义相反**, 属于必须改的那类问题。

### 3.2 候选与推荐

| 候选 | 读作 | 评价 |
|---|---|---|
| `frozen_version`(现状) | "冻结时的版本" | ❌ 诱导跨代比较; 且它是计数器而非 version 指针 |
| **`frozen_gen`** | "**冻结代**" | ✅ **推荐**: 保留 `frozen` 身份(追溯冻结来源), `gen` 明确"这是代数不是版本指针"; 依赖钉 N 代语义自然 |
| `compat_gen` | "兼容代" | ✅ 语义最准(它确实是兼容性代数); 但丢掉了"冻结"这一来源, 与三态的联系变弱 |
| `abi_gen` | "ABI 代" | ⚠️ 偏 ABI; 但它同时管**源码面**(签名/枚举), 不止 ABI |
| `soname` | — | ❌ 借用 ELF 术语, 但本 OS **静态链接、无 .so**, 会误导 |

**推荐 `frozen_gen`**; 若需求方更重视语义精确, 可退而用 `compat_gen`。

**版本串写法不变**, 仅字段名与叙述调整:

```
v FROZEN_GEN . MAJOR . MINOR . REVISE     例: v3.1.2.0
依赖: frozen_gen = 3        (精确, 必填)
       range     = ">=1.2.0" (只比较 M.m.r)
```

> **说明**: `[`r1/05`](05-version-model-frozen.md) §3.1 的字段名 `frozen_version` 随之改为 `frozen_gen`; 其余(两字段、范围固定 3 段、4 段范围非法)不变。

## 4. 状态机: 缺一条路径, 且解冻是**瞬态**

### 4.1 既有状态机确实没有"解冻"

`1-02` §2.6.2 的转移表只有 5 行, **没有 `FROZEN→(改)→FROZEN`**:

```
*→EXPERIMENTAL | EXPERIMENTAL→FROZEN | FROZEN→DEPRECATED | DEPRECATED→移除 | DEPRECATED→FROZEN
```

实测"解冻/重新冻结/unfreeze"在**既有 21 篇设计文档中 0 命中** ⇒ 纯新增机制(已在 [`r1/05`](05-version-model-frozen.md) A-13 登记)。

### 4.2 建议: 解冻 = **单元级的瞬态**, 不是第 4 个条目状态

**不要**把 `unfreezing` 加成第 4 个 `status` 值 —— 条目在解冻窗口内**仍然是"我们没打算放弃承诺"的**, 只是正在**重新谈判**。因此把瞬态放在**单元级**:

| 轴 | 取值 | 归属 |
|---|---|---|
| `status`(既有, 不变) | `experimental` \| `frozen` \| `deprecated` | **条目** |
| `freeze_state`(新增) | `unfrozen` \| `frozen` \| **`unfreezing`** | **单元** |

### 4.3 解冻窗口的三条规则

| # | 规则 | 理由 |
|---|---|---|
| 1 | `unfreeze <unit>` 需**最高门槛 RFC** | 解冻让**全部依赖方强制重新验证**, 影响面比单次签名变更更大 ⇒ 应纳入 `1-02` §2.2 已有的"最高门槛"行(sched_class / 插件描述符 / 注册表语义) |
| 2 | 窗口内可自由改/删/加条目; `refreeze <unit>` 时**若确有"已冻结条目的改/删"则 `FROZEN_GEN + 1`**, 否则**不 bump** | 精确对齐需求方"**已有接口发生变动**"—— 空解冻(改了又改回去/最终没动已有条目)不该让全体依赖方重钉 |
| 3 | **`br check --profile release` 在任何单元处于 `unfreezing` 时失败** | 防止"release 停在半谈判状态"—— 与 [`r1/05`](05-version-model-frozen.md) §8.4 的 release 门禁同轴 |

### 4.4 解冻路径与既有"软路径"的分工(两条改面路径)

| 路径 | 动作 | `FROZEN_GEN` | 依据 | 适用 |
|---|---|---|---|---|
| **软** | 面内演化: 语义变更 / 弃用 → RFC + 弃用周期, 不 unfreeze | **不变** | `1-02` §2.2 / §2.6.2 | 不破坏源码兼容的演化 |
| **硬** | **unfreeze → 改/删已有条目 → refreeze** | **+1** | 本轮规则 | 签名变更 / 删除 / 破坏性重排 |

> **澄清(须写进文档)**: 删除 frozen 接口 = 既有接口变动 ⇒ 走**硬路径**(`FROZEN_GEN+1`); **同时**仍须满足 `1-02` §2.6.5 的弃用周期。两条要求**独立**: 一个管兼容代, 一个管通知期。

## 5. ⚠ 关键陷阱: "新增无需解冻"只在**条目级**成立

### 5.1 问题

若在**单元级**笼统实现"新增无需解冻", 会让下面这一类比"新增"更危险的操作**绕过 `F`**:

> 给一个**已冻结的结构体**加一个字段。

这在直觉上是"新增", 但在 D14 的二进制兼容模型里是**修改**:

| 出处 | 原文 |
|---|---|
| `1-01` **D22**(行 132) | "动机 = D14: ops 布局入 golden, **后补字段 = 布局破坏**——**预留即免破坏**" |
| `1-02` §4.1 item 2(行 244) | "内联访问器…其**布局变更按硬门禁处理**" |
| `1-02` §4.1 item 4(行 246) | "**枚举 append-only** 进 golden; 位标志集合新增值只许 OR 进" |
| `1-02` §2.4(行 114) | "**枚举只追加、不重排**、不当位标志跨版本扩展" |

⇒ 既有设计**早已区分**两件事:

- **新增一个条目**(新函数/新枚举成员) = 安全的追加 ⇒ 无需解冻 ✅
- **改一个已有条目**(结构体加字段 / 枚举重排 / 签名变更) = **破坏承诺** ⇒ 必须解冻 ❌

### 5.2 判定必须落在**条目内部结构**上

因此 `br check` 不能只比"条目集合的差", 而必须:

```
对每个已冻结条目:
  条目集合新增?           -> append, 无需解冻
  条目自身内部结构变化?    -> modify, 必须解冻(即使"看起来是加了个字段")
```

**具体到条目 kind**:

| 条目 kind | 「追加」的形态(免解冻) | 「修改」的形态(**须解冻**) |
|---|---|---|
| `func` | 新增一个函数 | 签名变化 / 参数名进 strict 模式 / 语义变更 |
| `type`(struct) | 新增一个**独立**结构体 | **给已有结构体加/删/重排字段**(D22 明令 = 布局破坏) |
| `enum` | **末尾追加**成员 | **重排** / 复用旧位 / 删除成员 |
| `service` | 新增一个 service 名 | 已有服务的 ops 表加槽 / 改签名 |
| `macro` | 新增宏 | 改已有宏的值/定义 |

> **这条正是 [`r1/03`](03-tech-review.md) P0-2 的另一面**: 该 P0 指出 `macro`/`var`/`service` 条目**没有参与 hash 的字段**(故 `#define BR_MAX 16→4096` 算不出面变化)。如果那条不修, 本节这个陷阱**连检测手段都没有** —— 二者必须一起修。
>
> **D22 的启示**: 既有设计用"**预留槽位**"(`ioctl`/`suspend`/`resume` 预先占位)来避免"将来加字段"。在新模型下, 预留槽位的价值**翻倍**了 —— 它把"将来必须解冻"变成"现在就已存在", 从而让 `FROZEN_GEN` 更稳定。建议把"**冻结前应预留扩展槽**"写进冻结评审清单。

### 5.3 完整判定矩阵(含未冻结条目)

| 条目 status | 新增 | 改/删 | `FROZEN_GEN` |
|---|---|---|---|
| `experimental` | 自由 | 自由(可碎) | 不变(它没有承诺可破) |
| `frozen` | **免解冻** | **须解冻** | 仅"改/删"时 +1 |
| `deprecated` | 免解冻 | 移除须满足弃用周期 ⇒ 走硬路径 | +1 |

> **注意 `experimental` 行**: 改它**不 bump `FROZEN_GEN`**(无承诺可破), 但**面 hash 会变** ⇒ 仍须 `MINOR+1` 记录"面变了"。这与 [`r1/05`](05-version-model-frozen.md) §0.2 的段映射一致, 也再次说明 **hash 与 `FROZEN_GEN` 是两条独立证据**(§7)。

## 7. 连带结论: `FROZEN_GEN` 与 `hash` 的分工被这条规则**固化**

三者各司其职, 不可互替:

| 证据 | 回答 | 谁维护 |
|---|---|---|
| **`FROZEN_GEN`** | "**承诺被破坏过几次**"(权威、低频、需 RFC) | 工具强制(解冻/重冻序列) |
| **`hash`** | "**这个面具体长什么样**"(含追加, 高频) | 工具计算(IFACE-IR) |
| 条目 `status` | "**哪些条目受保护**" | 人工声明 + 状态机校验 |

**由此得到一条可直接写进 §6 的判定表**(替代原 §5.2 的 `iface_changed` 布尔, 该布尔已可删除, 见 [`r1/05`](05-version-model-frozen.md) §5.2):

| `FROZEN_GEN` | `hash` | 结论 | 需求方问题的答案 |
|---|---|---|---|
| 不变 | 不变 | 面完全未动 | — |
| 不变 | **变** | **纯追加 / status 转移 / experimental 改动** | "**是否增加接口?**" → 是 |
| **+1** | 变 | **已有条目被改或删** | "**是否变更/删除了某个接口?**" → 是 |
