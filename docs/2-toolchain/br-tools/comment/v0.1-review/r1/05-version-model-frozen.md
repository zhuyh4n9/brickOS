# br-tool v0.1 设计备忘 · 版本模型修订(`frozen_version.major.minor.revise`)

> **文件性质**: **设计备忘(memo)** —— 记录需求方本轮给定的版本号规则、其推演后果、必须一并修订的契约, 以及 3 个待拍板的叉。不是缺陷清单。
> **缘起(需求方规则, 原话)**:
> 1. 版本号规则修改为 `v frozen_version.major.minor.revise`
> 2. 对于 `frozen`, **只有解冻/重新冻结后更新**(已有接口发生变动), 一般新增接口无需变动
> 3. 重大版本更新时 `major` 更新; 4. 小功能更新后 `minor` 更新; 5. 修订 bug 后 `revise` 更新
> 6. **因此版本依赖必须指定具体的 `frozen` 版本号; `>=`/`>`/`=` 只比较 `major.minor.revise`**
> **影响面**: 本规则**推翻**草案 §5.2 的推进矩阵与 §7.4 的区间语义, 并**同时解掉** [`r1/01`](01-self-review.md) P0-1/P0-2 与 [`r1/03`](03-tech-review.md) P0-4(三个 P0 同源: 原 `a` 段语义未定死)。
> **状态**: 待拍板 —— §4 的 F1–F3。
> **基线**: 草案 commit `bb99dbc`。

## 0. 规则的规范性重述

```
版本 = v F . M . m . r        F = frozen_version, M = major, m = minor, r = revise

F  仅由「解冻 → 改动已有接口 → 重新冻结」更新; 新增接口一般不动 F
M  重大版本更新(产品能力代际, 人工决策)
m  小功能更新
r  修订 bug

依赖 = (frozen_version 精确值, 范围表达式)     范围表达式只作用于 M.m.r
       F 必须精确指定, 不可用 >=/>/= 表达
```

### 0.1 与原草案的段名对照

| 原草案 | 新规则 | 语义变化 |
|---|---|---|
| `a` 接口兼容代数 | **`F` frozen_version** | 由"推论"变为**由冻结事件强制**(解冻/重新冻结) |
| `b` 主版本 | **`M` major** | **与接口破坏解耦** —— 破坏性接口变更只 bump `F`, 不再 bump `M` |
| `c` 次版本 | **`m` minor** | 保留 |
| `d` 修订 | **`r` revise** | 保留, 且**明确为人工声明**(见 §5.3) |

### 0.2 核心分歧点: `F` 与 `M` 被解耦

这是本规则**最重要的后果**, 也是它解掉三个 P0 的原因:

- **原模型**: `M` 只在冻结面破坏时 +1 ⇒ `F≡M-1`(恒同步) ⇒ 四段退化为 `F.0.m.r`([`r1/01`](01-self-review.md) P0-1 枚举 165 个可达版本, `b` 恒为 0)
- **新模型**: `F` 由**接口契约**驱动, `M` 由**产品演进**驱动, 二者**完全独立** ⇒ 可同时出现 `F=3,M=1`(接口破了一代但产品大版本没动)与 `F=1,M=2`(产品翻代但接口没动)

| 事件 | 原模型 | **新模型** |
|---|---|---|
| 破坏性接口变更 | `a+1, b+1` | **`F+1`**(M 不动) |
| 重大产品版本 | 无独立触发(被冻结面绑架) | **`M+1`**(F 不动) |
| 新增接口 | `c+1` | **`m+1`**(F 不动) |

## 2. 语义澄清: 两条独立轴, 缺一不可

新规则**不**取代三态(`experimental`/`frozen`/`deprecated`), 二者正交:

| 轴 | 回答 | 取值 |
|---|---|---|
| `status` | **治理状态**: 这个面受不受保护? | experimental / frozen / deprecated |
| `F` | **兼容代**: 受保护的面被动过几次? | 0, 1, 2, … |

**`F=0` 是双义的, 必须靠 `status` 消歧**(记入待决 F2):

- `F=0` + `status=experimental` = **尚未冻结**(`1-02` D15: M3 前全部如此)
- `F=0` + `status=frozen` = **首次冻结, 尚未被重新冻结过**

> **推论**: 首次冻结(`experimental→frozen`)**不 bump `F`** —— 因为需求方规则说 `F` "只有解冻/重新冻结后更新(已有接口发生变动)", 而首次冻结不含"已有接口变动"。`F` 从 `1` 起才表示"重新冻结过一次"。

## 3. 必须一并修订的契约

### 3.1 依赖语法(两字段, 为落实"必须指定具体 frozen 版本号")

```toml
[[dep]]
name           = "ability/vfs-core"
frozen_version = 3            # 必填, 精确匹配; 0 = 提供方尚未冻结
range          = ">=1.2.0"    # 只比较 major.minor.revise(固定 3 段)

[[compat.requires_iface]]
id             = "ability/vfs-core#file"
frozen_version = 3
range          = ">=1.2.0"
```

**三点设计取舍**:

| 取舍 | 理由 |
|---|---|
| **两字段而非单字符串** | `F` 精确、`M.m.r` 范围 —— 两种语义混在一个字符串里无法校验(且违反 `BRV-D2` "禁止隐式"); 拆开后可分别报错 |
| 字段名 `frozen_version` 而非 `frozen` | 避免与 `status = "frozen"` 混淆(一个是代次数字, 一个是治理状态) |
| 原 `version = ">=0.1.0.0"` 改名 `range` | 与 `[plugin].version`(自身版本)**区分开**, 避免"依赖版本 vs 自身版本"同名歧义 |

### 3.2 区间语义: 只有 3 段, 且原 `^`/`~` 争议消失

| 写法 | 语义 | 评价 |
|---|---|---|
| `>=M.m.r` / `>M.m.r` / `=M.m.r` / `<M.m.r` / `<=M.m.r` | 按 `(M,m,r)` **字典序**比较 | ✅ 需求方明确点名的操作符集 |
| `~M.m.r` | 允许 `r` 升, `m`/`M` 固定 | 可选(语义等价于 `>=M.m.r,<M.(m+1).0`) |
| `^M.m.r` | 允许 `m`/`r` 升, `M` 固定 | 可选(等价于 `>=M.m.r,<(M+1).0.0`) |
| **`>=F.M.m.r`(4 段)** | **非法** | `BRV-VER-0006` —— 直接落实"只比较 M.m.r" |

**关键收益**: 原草案里 `^` 与 `~` 因 `b` 是 `a` 的函数而**外延相同**([`r1/01`](01-self-review.md) P0-2 实测 28=28)。新模型下 `F` 已被精确钉住, `M` 恢复独立 ⇒ **`^` 与 `~` 自然分开**(`^` 跨 `m`, `~` 不跨), 争议自动消解。二者是否保留为语法糖, 属可选优化, 不影响正确性。

### 3.3 「解冻 / 重新冻结」是**新机制**, 既有状态机没有它

实测: `解冻`/`重新冻结`/`unfreeze` 在**既有 21 篇设计文档中出现 0 次**。而 `1-02` §2.6.2 的转移表只有:

```
*→EXPERIMENTAL | EXPERIMENTAL→FROZEN | FROZEN→DEPRECATED | DEPRECATED→移除 | DEPRECATED→FROZEN
```

**没有 `FROZEN→(改)→FROZEN` 这条路径** ⇒ 必须新增。由此得到**两条改变受保护面的路径**(建议明确写进 `1-02` §2.6.2):

| 路径 | 动作 | `F` | 依据 | 适用 |
|---|---|---|---|---|
| **A 软路径** | 面内演化: 语义变更/弃用 → RFC + 弃用周期 | **不变** | `1-02` §2.2 阈值表 / §2.6.2 | 不破坏源码兼容的演化 |
| **B 硬路径** | **解冻 → 改动已有接口 → 重新冻结** | **`F+1`** | 本轮规则 | 签名变更 / 删除 / 破坏性重排 |

**两条澄清(必须写进文档, 否则会被误读)**:

1. 删除 frozen 接口 = **既有接口变动** ⇒ 走 **B 路径**(`F+1`); **同时**仍须满足 `1-02` §2.6.5 的弃用周期 —— 两个要求**独立**, 一个是兼容代, 一个是通知期。
2. **解冻应由最高门槛 RFC 授权**: `1-02` §2.2 阈值表已有"最高门槛"行(sched_class / 插件描述符 / 注册表语义)。解冻会让**全部依赖方强制重新验证**, 影响面比单次签名变更更大 ⇒ 建议把"解冻/重新冻结"加入该行。

## 4. 三个必须拍板的叉

### F1 — `F` 的粒度: 插件级 vs **冻结批次/接口单元级**?(最关键)

需求方把 `F` 描述为**插件版本的第一段**(插件级)。但既有文档的冻结粒度是**按批次的**:

| 依据 | 原文 |
|---|---|
| `3-01` §15 | "golden 文件划分(§1)= **分批冻结的最小单元**"; 第一批 `br-mem`/`br-mm`/`br-irq`/`br-svc`, 第二批 `br-sched`, M4 后 `br-irq` 增补 |
| `1-02` §2.6.4 | "**分组 = 冻结批次单元**(`3-01` §15): 每文件独立升格, **互不绑架**" |
| `1-02` §3.2 | 人读层是**模块级**且**带版本**: `provides/requires: posix-fd@1.2` |

**插件级 `F` 的代价**: 某插件同时提供两个面(例如框架件既提供 core 面又提供自身 ops 面), 改动其中一个就 bump 插件级 `F` ⇒ **另一个面的全部依赖方被迫重新钉版** ⇒ 直接违反 `1-02` §2.6.4 的"**互不绑架**"。

| 方案 | 说明 | 评价 |
|---|---|---|
| **A 单元/批次级(倾向)** | `F` 归属接口单元; **依赖必须针对单元**钉 `F_u`; 插件版本 `F = max(F_u)` 仅用于显示与结构依赖 | ✅ 与 `3-01` §15 + `1-02` §2.6.4 一致; 与已有"模块级 `posix-fd@1.2`"一致 |
| B 插件级 | `F` 归属插件, 全部单元共享一个 `F` | 简单, 但违反"互不绑架"; 一个面的破坏传染全插件依赖方 |

> **注意**: 方案 A 下, 插件的 `vF.M.m.r` 仍然存在(注册表/显示/结构依赖用), 只是 `F` 变为 `max(F_u)` 的**汇总量**; 而"必须指定具体 frozen 版本号"的强制落在**接口依赖**(`requires_iface`)上 —— 这也正好对应需求方"接口发布"的语境。

### F2 — `F=0`(尚未冻结)的依赖怎么办?(不解决则 v0.1 无法启动)

`1-02` D15 明确 **M3 之前不冻结任何东西**, 而 v0.1 位于 M0/M1 之间 ⇒ **v0.1 期间一切 `F=0`**。若不处理, "依赖必须指定具体 `F`" 这条规则在 v0.1 会**把 M0–M2 全部判红**(任何插件都不能依赖任何插件)。

| 方案 | 说明 | 评价 |
|---|---|---|
| **A 允许 `F=0`, 给 warning(倾向)** | `BRV-VER-0004` warning; 语义 = "依赖未受保护的面, 接受其任意变动" | ✅ 使 M0–M2 可行; 语义诚实 |
| B 禁止依赖未冻结面 | 强制先冻结才能被依赖 | ❌ **杀死 M0–M2**(与 D15 直接冲突) |

### F3 — 结构依赖(`init`/`runtime`/`type`)是否也钉 `F`?

| 方案 | 说明 | 评价 |
|---|---|---|
| **A 结构依赖不钉 `F`, 只给 `range`(倾向)** | 结构依赖关心的是"初始化顺序/存在性", 与接口兼容代无关 | ✅ 避免把接口代次强加到结构关系上 |
| B 结构依赖也钉 `F`(插件级 `max`) | 统一形式 | ⚠️ 会在 `F1=A` 下产生粗粒度误报 |

## 5. 连带影响

### 5.1 `hash` 的地位**上升**: 因为新增接口不 bump `F`

新规则下, **同一 `F` 内允许新增接口**(需求方明确"新增接口一般不动 `F`")⇒ 两个构建可能同 `F.M.m.r` 但**面不同**。此时**唯一能区分二者的就是 `iface_hash`**。

**后果**: [`r1/03`](03-tech-review.md) **P0-2**(hash 无文法、`macro`/`service` 条目无 sig 字段、`typedef` 表不存在)**从"重要"升级为"阻塞"** —— 它是同 `F` 内区分不同面的**唯一手段**。建议把 P0-2 提到修复批次 1。

### 5.2 可删除的原设计: `iface_changed` 布尔

原草案为回答需求方"是否变更/删除了某个接口", 引入布尔字段 `iface_changed`(§5.2 行 357)。新模型下该信息由 **`F` 是否变动 + `hash` 是否变动** 完整确定:

| `F` 变动 | `hash` 变动 | 含义 |
|---|---|---|
| 否 | 否 | 面未变 |
| 否 | **是** | **纯新增**(或状态转移) —— 需求方"是否增加接口?" |
| **是** | 是 | **已有接口变动** —— 需求方"是否变更/删除了接口?" |

⇒ **建议删除 `iface_changed`**(减少一个冗余真值, 符合 `4-03` 单一事实源纪律)。

### 5.3 `M.m.r` **不再假装可机器推导** —— 工具职责边界变清晰

需求方规则给了 `M`/`m`/`r` 的**人类语义**("重大版本更新"/"小功能更新"/"修订 bug"), 而这些事件 **v0.1 无编译、无符号、无测试 ⇒ 工具看不见**。因此职责边界为:

| 段 | 谁决定 | 工具做什么 |
|---|---|---|
| **`F`** | **工具强制** | 由 `freeze`/`unfreeze` 命令序列产生; 拒绝手工任意 `--set`(或要求 `--note`) |
| `M` / `m` / `r` | **人声明** | `br ver bump --rule major\|minor\|revise` 辅助 + 写回; 校验单调不回退 |
| `hash` | **工具计算** | 由 IFACE-IR 规范化算出 |

> 这**顺带解掉** [`r1/01`](01-self-review.md) **P0-3**(原 `d` 段在 v0.1 无任何自动信号源, 且与幂等纪律冲突): `r` 本就是人工声明, 不再需要"自动检测实现变更"; `publish` 的幂等定义也随之简化为"**声明面与快照相同 ⇒ 空操作**"([`r1/03`](03-tech-review.md) P0-1 的修法)。

### 5.4 跨 `F` 比较**无意义**(须写明)

`F` 精确匹配 ⇒ 依赖求解**永不跨 `F` 比较**。因此:

- `(F,M,m,r)` **字典序**只可用于**同一 `F` 内**排序/展示
- 跨 `F` **不存在"更新/更旧"**: `F=4` 是在 `F=3` 之后出现, 但 `F=4` 可能**删掉了** `F=3` 的接口 ⇒ 对依赖方而言是"**不兼容的另一代**", 不是"升级"
- 迁移语义由 `deprecated` + 弃用周期承担, 不由版本序承担
