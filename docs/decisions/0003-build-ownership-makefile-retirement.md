# 0003: 构建归属转移 —— 顶层 `Makefile` 只编 tool, 项目由 `brickie` 组织

> 状态: **方向已定, 版本号待拍**(见 §5 待拍项 1) | 影响面: **prototype 分支的顶层 `Makefile` 职责** + CI 入口 + `br-wa-entry-001` / `br-wa-boot-001` 的退出条件
> 格式依据: `1-02` §2.2(动机 / 设计 / 替代方案 / 兼容性影响)
> 相关: `2-02` §1(职责 / 非职责表)、§3 **BR-D4**(构建后端边界)、§7(M0–M5 演进); `1-01` §13(开发工作流); ADR-0002(自洽工具集)

## 1. 动机

1. **顶层 `Makefile` 现在越权了, 而且是静默的**。它同时在做两件设计上分属不同所有者的
   事: ①**编自己**(构建 `tools/brickie/`, 天经地义); ②**组合项目**(哪些源码进镜像、
   链接脚本怎么来、`platform/` 直编 —— 而 `2-02` §1 的职责表把"插件发现 / manifest 解析 /
   闭包求解 / 拓扑与环检测 / 生成物 / 构建编排"**全部划给 `brickie`**)。
   现状之所以成立, 只是因为 `brickie` 还没长出这些能力(`br-wa-entry-001` /
   `br-wa-boot-001` 就是这个缺口的两条登记)。
2. **`Makefile` 表达不了项目的组合语义**。依赖闭包、`compat_gen` 精确匹配、分类学禁则、
   相位单调、资源预算 —— 这些是 `2-02` §1 划给求解器的判断, `make` 的语法里没有位置放它们。
   继续把项目构建留在 Makefile, 等于把这些判断**要么写死、要么丢掉**。
3. **"工具是唯一手写构建入口"是一条可检验的纪律**。终局形态里, 仓库里手写的构建入口只有
   一个(编 `brickie`), 其余构建文件**都是 `brickie` 的生成物** —— 与 C6"生成物不手改"、
   BR-D5"状态目录"、`2-02` §4 建议 3 是同一套纪律的不同侧面。

## 2. 决策(方向)

**终局**: 仓库里**手写的构建入口只剩"编 `brickie`"**; 项目的组织与构建由 `brickie` 承担。

| 面 | 现在 | 终局 |
|---|---|---|
| 顶层 `Makefile` | 编 tool **+** 编镜像 | **只编 tool** |
| 镜像怎么编 | `Makefile` 里的手写规则(`core/src/*.c`、`platform/src/*/*.c`、`link.ld`) | `brickie` 先求解声明面, 再**生成**构建输入, 然后驱动后端 |
| 构建后端 | 就是那个手写 `Makefile` | **BR-D4 倾向 A**: `brickie` 生成 + 编排, **make** 干活(备选 B: 直出 **ninja**) |
| 插件树组织 | 无(`platform/` 被直编) | `brickie` 按布局约定发现 / 校验 / 拓扑(`4-02`, `3-05` §2.2) |
| CI 入口 | `make` / `make smoke` | `brickie build` / `brickie run` / `brickie check`(`1-01` §13 的工作流) |

**三点必须写清楚, 否则会被误读**:

1. **`Makefile` 不会被消灭, 它被降级为生成物**。终局里 `build/gen/` 下仍会有 make/ninja 文件
   (BR-D4 的 A/B), 但它们由 `brickie` 生成、**不手改**。被取消的是"**人手写的项目构建入口**"这一身份。
2. **"只编 tool"恰恰把宿主编译器变成承重墙**。`brickie` 的 L2 生成器是**宿主** C++;
   而 Arm GNU Toolchain 只产**目标**代码(ADR-0002 §5-1)。所以终局形态会让
   "宿主工具链是否也需要 self-contained"从"将来的事"变成"必须回答的事" ⇒ 见 §5。
3. **这不是本 ADR 新提出的方向, 而是给既有分工补一条可执行的时间线**。`2-02` §1 早已把
   构建编排划给 `brickie`, `1-01` §13 早已把工作流写成 `brickie init/add/build/run/test`。
   本 ADR 只新增一件事: **顶层 `Makefile` 的退役路径**。

## 3. 过渡路径(每步都有可验收判据, 不许"差不多切过去了")

| 步 | 内容 | 出口判据(可验收) | 依赖 |
|---|---|---|---|
| **S0** | 现状: `Makefile` = tool + 镜像 | `make` / `make smoke` 全绿; `make check-build` 全绿 | ✅ 已达成 |
| **S1** | `Makefile` **生成物化**: 镜像那一半的规则搬进 `build/gen/`, 由 `brickie gen` 产出; 手写 `Makefile` 只 `include` 它 | `build/gen/Makefile` 是生成物(带 `brickie:generated` 标记); 手写 `Makefile` 里**没有** `core/src` / `platform/src` 的字面路径 | brickie 的 `gen`(checklist C-03)+ 描述符生成 |
| **S2** | **后端可换**: 同一份声明面能出 make 或 ninja(BR-D4 的 A/B) | 两种后端产出的镜像**逐字节一致**(或差异有书面理由) | brickie 的构建编排(设计 §14 的"编译", 现排 v0.3) |
| **S3** | **CI 换入口**: CI 从 `make` 改为 `brickie build` | CI 里不再出现裸 `make`; `brickie build` 覆盖 check + 生成 + 编译 | S1+S2 |
| **S4** | **顶层 `Makefile` 只编 tool** | `make` 的唯一产物是宿主工具(`build/host/<host-arch>/<host-os>/bin/brickie-gen`, 见 ADR-0004; 源码仍在 `tools/brickie/cxx/`); `br-wa-entry-001` 注销 | ADR-0002 §5-1 有结论 |

**S4 的验收里有一条容易被忽略的**: 那时 `make` 已不产镜像, 所以
`br-wa-toolchain-001`(外部交叉编译器)的作用域要**跟着缩小** ——
"编 tool 不需要交叉编译器", 交叉工具链变成 **`brickie` 运行期的输入**(来自 `prebuilts/toolchain/`)。
这条要在注销该 WORKAROUND 时一并改掉, 否则会留下一条名不副实的登记。

## 4. 替代方案与否决

| 方案 | 评价 |
|---|---|
| ❌ **保留手写 `Makefile` 作为最终构建入口** | 与 `2-02` §1 的职责表正面冲突; 且 Makefile **表达不了**闭包求解 / 分类学 / 版本区间 —— 留在那里只能靠人肉维护那些判断, 正是 `br-wa-entry-001` 现在的形态 |
| ❌ **立刻切换(S4 现在做)** | `brickie` 目前只有 `new`(checklist §5.2 的 P0 半批), `check` / `gen` / 构建编排都没有 ⇒ 立刻瘫痪。**没有可执行的中间态** |
| ◐ **保留 Makefile 但让它 `include` 生成物(S1 即终局)** | 这是本 ADR 的一个**合法停靠点**: 若 S2/S3 长期不落地, S1 已经拿到了"组合语义在 brickie、编译机械在 make"的全部好处。可作为**阶段性终点**而非必须走到 S4 |
| ❌ **改成 CMake / Meson 等通用构建系统** | 换一个同样表达不了组合语义的手写入口, 问题原样保留; 且 `2-02` §3 BR-D4 已就此定过向(否决 C 自研, 倾向 A 用 make) |

## 5. 待拍项

1. **版本号**: "v0.2 之后"里的 `v0.2` **指哪个版本号, 待拍**。已知冲突:
   - 设计 `brickie-v0.1.md` §14 把**编译(构建编排)排在 brickie v0.3**, 而 **v0.2 是"接口依赖扫描检查"**;
   - 原型的版本号则是 `prototype-v0.1.0`。
   于是"v0.2 后 `Makefile` 只编 tool"有两种读法: **(甲)** 指原型 v0.2.0 ⇒ 需要把设计里
   brickie v0.3 的"编译"能力**前移**; **(乙)** 指 brickie v0.2 ⇒ 与 §14 直接冲突, 须一并改 §14 演进表。
   **本 ADR 不替它选**(用户裁定: 先记方向)。**在此之前, S1 是唯一无依赖的可开工步骤**。
2. **宿主编译器的自洽性**(与 ADR-0002 §5-1 同一条): 终局里 `Makefile` 只编 tool, 而 tool 是宿主程序
   ⇒ 若要"全链路不依赖外部工具", 必须再纳一件宿主编译器(LLVM/clang 那条路, 或宿主 gcc 的 prebuilt)。
   **另一半见 ADR-0004**(自举种子 `prebuilts/seed/brickie/...`): 种子解决"**没有宿主编译器时如何起步**",
   但**不替代**"用受治理的宿主编译器重建" —— 两者互补(S4 的 `make` 仍需宿主编译器, 种子只是让 S4 之前/之外也能跑)。
3. **`br-wa-boot-001` 的处置**: 该 WORKAROUND 的还债动作写的是"`br_core_main` 的归宿不是长大而是被拆掉"。
   拆掉它的前置是 `3-05` 的 plugin_manager, 而 plugin_manager 的输入是 `brickie` 的生成物
   ⇒ **S1 是它的前置**。这条依赖关系目前没写在任何地方, 应补进 `WORKAROUNDS.md` 或 `1-03` 路线图。

## 6. 兼容性影响

| 面 | 影响 |
|---|---|
| `Makefile` 目标面 | 逐步缩减: `run`/`smoke`/`size`/`disasm` 最终迁给 `brickie`(`1-01` §13)。**缩减期两条路径必须并存**, 否则开发中断 |
| CI | S3 起入口从 `make` 变为 `brickie build`; 三层门禁(`1-02` §2.3)由 `brickie` 编排, 不再由 Makefile 拼 |
| WORKAROUND | `br-wa-entry-001` 在 S4 注销; `br-wa-toolchain-001` 的作用域随 S4 缩小(见 §3); `br-wa-boot-001` 见 §5-3 |
| 设计侧 | 无契约改动。但本 ADR 给 `2-02` §7 的 M0–M5 表提供了 prototype 侧的对应台阶, 回灌时可引用 |
| 现有产物 | 无: `build/` 是派生目录, 两条路径产出的镜像在过渡期需**逐次比对**(这正是 S2 的出口判据) |
