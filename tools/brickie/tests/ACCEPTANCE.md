# brickie v0.1 acceptance matrix (V-1…V-21)

> Purpose: map the 19 acceptance items of `brickie-v0.1.md` §10 to **executable cases**, as the
> blueprint and regression baseline for `tests/run.sh`. Each row gives: criterion / case shape / required fixture /
> observation point (exit code + code + text).
> Status legend: ⬜ not written ｜ 🟡 partial ｜ ✅ covered (executable case exists and measured all green) ｜ ⏸ N/A / pending decision.
>
> **Current state (measured)**: `bash tests/run.sh` = **pass 631 / fail 1** (~15s class; includes the 27 V-18 cases and
> the ~70 cases of the §V-B build family). The only failure is `new-json` **protocol snapshot baseline stale** — another subagent (F1) changed
> `rust/src/plan.rs` + `templates/descriptor/**` mid-flight, so `brickie new --json`'s `vars` gained
> 14 keys (`abi_id` / `api_rev` / `deps_array` / `deps_expr` / `early_proto` / `gen_total` /
> `init_hook` / `init_proto` / `plugin_type_id` / `res_ram_kib` / `res_stack_kib` /
> `sched_class_id` / `start_proto` / `subkind_id`), and no key was removed.
> **Disposition (division-of-labour ruling)**: the snapshot baseline is regenerated by the **main agent at integration time**
> (`make -C tools/brickie test-snap` + key-by-key diff review) — the baseline is only trustworthy once tool-side changes are frozen.
> **Unrelated to §V-B / the build family** (V-B all green).
> Binary resolution matches `python/brickie/native.py`: `build/host/<triple>/bin` first,
> falling back to `prebuilts/seed/brickie/<triple>/bin`; cases explicitly inject `BRICKIE_CORE`/`BRICKIE_GEN`.
> Snapshot baselines live in `tests/snap/*.json` (N-4) and are regenerated with `make test-snap`.

## 4. Implementation defects found by measurement

> Convention: a **defect** = implementation behaviour that contradicts the written design/contract
> requirements (excluding "the test expectation was wrong"); tests are not loosened because of them —
> the affected cases assert per the ruling (see §3), and defects are recorded separately here.
>
> **Both were fixed before merge** (D-1: the `prebuilts/` owner re-issued the seed; D-2: `brickie-core`
> unified the effective-freeze-state rule); after the fix `make tools-test` = 542/0 and `make tools-prebuilt-check`
> shows all three ok. The **original repro and expected/actual** are kept below as regression criteria (change it back and these two reappear).

### D-1 The checked-in bootstrap seed lags the source ⇒ the bootstrap path is unusable on a fresh checkout

* Repro:
  ```sh
  cd prototype
  make tools-prebuilt-check          # read-only gate
  # or ask the seed core directly:
  mkdir -p /tmp/t && cd /tmp/t && mkdir -p provider/x && printf 'schema = 1\n[plugin]\nname = "provider/x"\nplugin_type = "ability"\napi_type = "native"\nlang = "c"\nsubkind = "service"\nphase = "late"\nversion = "0.1.0.0"\n[compat]\ncore = ">=1.0.0"\nhash_scope = "decl"\ntruth = "decl"\n' > provider/x/brick.toml
  echo '{"protocol":1,"command":"check","root":"'"$PWD"'"}' \
    | /home/zhuyh/workspace/unikernel-dev/prototype/prebuilts/seed/brickie/x86-64/linux/bin/brickie-core
  ```
* Expected: `make tools-prebuilt-check` all ok; the three seed files `{brickie,brickie-gen,brickie-core}` match
  this build ⇒ a checkout without `build/` can still run the whole command surface.
* Actual: `make tools-prebuilt-check` reports
  `FAIL: bootstrap seed lags the source: prebuilts/seed/brickie/x86-64/linux/bin/brickie` and
  `.../brickie-core` (only `brickie-gen` matches); the seed `brickie-core` answers `check` with
  `exit_code 2` + `error: - command check not implemented yet (check.rs(agent-B): check)` —
  it is the **first-cut** build (without `check`/`closure`/`iface-*`).
* Impact: `prebuilts/seed/**` is the only bootstrap path for "a checkout without g++/cargo" ⇒ on that path
  `brickie check` / `dep closure` / `iface *` are all unusable; the V-9 case's "seed single-file entry"
  was still all green only because it **explicitly uses the `build/host/<triple>/bin` core/gen** per lookup order.
* Disposition: **fixed** — `make tools-prebuilt` re-issues the three seed files (byte-identical to this build);
  now on a checkout without `build/`, the single-file seed `brickie` can run `check`/`closure`/`iface *`.

### D-2 `iface show` reports the "declaration-surface freeze state" inside an unfreeze window, inconsistent with window state/gates

* Repro:
  ```sh
  cp -r tools/brickie/tests/fx/unfreeze /tmp/fz && cd /tmp/fz && echo rfc > rfc.md
  export BRICKIE_CORE=…/build/host/x86-64/linux/bin/brickie-core BRICKIE_GEN=…/brickie-gen PYTHONPATH=…/python
  python3 -m brickie iface publish provider/crypto#crypto
  python3 -m brickie iface unfreeze provider/crypto#crypto --note rfc.md
  python3 -m brickie iface show provider/crypto#crypto --json
  python3 -m brickie check --profile release
  grep freeze_state api/iface/provider/crypto/crypto.toml
  ```
* Expected: `iface show` uses the **same effective freeze state** rule (declaration OR snapshot) as
  `check`/`publish`/snapshots, so inside a window it should show `unfreezing` (`rust/README` §10 S-19 already writes this rule as "publish preserves the effective freeze state").
* Actual: on-disk snapshot `freeze_state = "unfreezing"` and `check --profile release` correctly reports
  `BRV-IFACE-0009`; but `iface show --json` has `data.unit.freeze_state = "frozen"`,
  `data.freeze_state` missing (text shows "freeze state: frozen"), `source = "snapshot+declaration"`
  ⇒ **a reader would think the unit is not in a window**.
* Impact: presentation-layer misleading (verdict unchanged); `iface status` only compares hashes, so `consistent=true` reports nothing either.
* Disposition: **fixed** — `iface list`/`iface show` now use the same
  `effective_freeze(declaration, snapshot)` rule as `check`/`publish`/`ver show`; inside a window `iface show --json` now gives
  `data.freeze_state = "unfreezing"`, `data.unit.freeze_state = "unfreezing"`, plus two new fields
  `declaration_freeze_state` / `snapshot_freeze_state` that explicitly separate "declaration vs publication record"
  (the protocol snapshot `snap/iface-show.json` was updated accordingly).

## 5. How to run

```sh
cd prototype
make tools                     # build L5/L2 only (host g++, no cross toolchain)
make tools-test                # generator selftest + tests/run.sh (includes V-18)
make -C tools/brickie test-purity   # run only the three V-18 criteria
make -C tools/brickie test-v        # verbose mode
make -C tools/brickie test-snap     # regenerate tests/snap/*.json (update protocol baselines)
```

`tests/run.sh` needs only: `build/host/<triple>/bin/{brickie-core,brickie-gen}` (or the seed),
system `python3`, and coreutils. `cc`/`g++`/`cargo`/`nm` are **not** required to be present.
