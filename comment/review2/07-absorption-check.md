## 2. v0.4 评审意见核对(1 条——已响应, 以更优方案替代字面建议)

> 意见原文: "Service 插件应该在 Interface 插件上, APP 插件下"(即服务层位于接口层之上、APP 之下, 服务可消费接口 API)

**落实方式: v0.5 D18 修正案(POSIX 双角色拆分), 未按字面采纳。**

- 字面方案的问题(文档 §7.5 论证成文): 依赖箭头=重新验证的方向——若服务依赖接口皮肤, 每换一次 API 皮肤都要重验网络栈/crypto 等贵资产(验证经济学)。
- 实际采纳: **svc-posix**(POSIX 运行时)从接口插件降为**普通服务**——三方中间件(sqlite/curl 类)可声明依赖它, **评审的真实诉求(中间件可用 POSIX)被完整满足**; `iface-posix` 保留为**严格叶子薄皮肤**(仅再导出+stdio/errno 接线)。
- 配套治理: 铁律"能力插件永不依赖接口插件"退役, 由四条治理规则取代(§7.2: 单向流/init 无环/共享状态唯一主人/符号独占); §7.6 给出 sqlite **双模式移植**(A 直链 svc-posix ~0 增量 / B native VFS 后端 ~600 行), M2 以 sqlite 模式 A 作为移植性验证。
- 设计同时诚实记录代价(§7.5): svc-posix 引力中心风险/native API 使用萎缩(Unikraft 教训)及缓解措施。

**判定: ✅ 已响应, 偏离有据**——评审的意图被满足, 字面层级被论证过的更优结构替代, 且替代理由、代价、缓解全部成文。

## 4. 文档集质量走查

### 4.1 发现的缺陷(建议修正, 均为低成本文档修复)

| # | 缺陷 | 位置 | 说明 |
|---|---|---|---|
| 1 | **trace 记录长度矛盾** | `03-debug` §1 vs 主文档 §11 / `02-roadmap` | 三处声称"定长 **16B** 记录", 但 `tg_trace_evt_t` 实际 = 4(tsc)+2(evt)+1(ctx)+1(narg)+12(arg[3]) = **20B**。需二选一: 改口径为 20B, 或收敛为 arg[2](=16B) |
| 2 | **插件段名不一致** | 主文档 §4.4/§6.1/§9 用 `.tg_plugins`; `08` §13.3(CA-10)与 `12-plugin-mgr` §2.2 用 `.tg_plugin` | 链接段名是元契约(D14 布局纪律), 必须唯一——建议统一为 `.tg_plugin`(与 `__start_/__stop_` 边界符号例示一致) |
| 3 | **生命周期相位表述不一致** | 主文档 §6.2 "EARLY→CORE→LATE→APP"vs `12-plugin-mgr` "EARLY(PRE_ARCH/PIC/ARCH)/CORE/LATE 三相" | 相位数与 EARLY 细分口径未对齐; 且描述符回调(early_init/init/start)与相位名的映射未成文——12 成文时需统一 |
| 4 | 错字 | `07-concrete-fs` §8 "ioct/PM 钩子" | → "ioctl/PM 钩子" |
